Securing the OMA
REST API

A proxy-layer authentication architecture using oauth2-proxy and Keycloak, with zero modifications to the application code.

oauth2-proxy v7.15.1 Keycloak / OIDC Device Flow for scripts
01
Context

The Problem

Before

  • All /api/* endpoints were publicly accessible

  • No way to identify who is calling the API

  • No token-based access control for scripts or pipelines

  • Modifying Django for auth = risk + maintenance burden

Goal

  • Enforce authentication on /api/* without touching Django

  • Support both browser users and scripts / pipelines

  • Delegate identity to the institutional Keycloak instance

  • Keep secrets server-side, never expose them to clients

02
Architecture

The New Stack

Internet
→
nginx
:80 (public)
→
Django
:8000
└─ auth_request →
oauth2-proxy
:4180 (internal, auth only)

nginx

Public entry point. Routes all traffic. Uses the auth_request directive to validate /api/ calls. Bypasses auth for browser AJAX from the website (sec-fetch-site: same-origin). Redirects browsers and returns 401 JSON for external clients.

oauth2-proxy

Internal auth service (forward-auth mode). Validates session cookies and Bearer tokens via its /oauth2/auth endpoint. Returns 200 or 401 to nginx's auth_request subrequests. No longer proxies traffic.

Django

Unchanged. Receives X-Auth-Request-User and X-Auth-Request-Email headers from the proxy if needed for future per-user logic.

Access Control

Public vs Protected Routes

Route Auth Required Notes
/oma/  /static/  /media/  /All/ Public Browser interface, assets
/api/auth/device  /api/auth/token Public Exact-match nginx locations, proxy to Keycloak (device flow + token exchange)
/api/* · website AJAX Passes sec-fetch-site: same-origin set by the browser → /_auth_check returns 200, no oauth2-proxy call
/api/* · browser navigation 302 sign-in sec-fetch-mode: navigate with no session → redirect to /oauth2/sign_in
/api/* · external client, no/invalid token 401 JSON curl, scripts: no sec-fetch-site header → oauth2-proxy validates → 401 JSON
/api/* · valid Bearer token Allowed oauth2-proxy validates token → request proxied to Django

Access Pattern · Browser

Browser Access

  • 01

    User navigates to https://oma.example.org/api/...

  • 02

    oauth2-proxy detects no session → redirects to Keycloak login page

  • 03

    User authenticates (password, OTP, passkey, or any IdP configured in Keycloak)

  • 04

    Keycloak redirects back to /oauth2/callback with an authorization code

  • 05

    oauth2-proxy exchanges code for tokens, sets an encrypted session cookie

  • 06

    Browser is forwarded to the original URL — fully authenticated

05
Access Pattern · Scripts & Pipelines

Programmatic Access
OAuth 2.0 Device Authorization Grant

  • 01

    POST /api/auth/device → receive device_code + browser URL

  • 02

    Script prints the URL. User opens it and authenticates once in browser.

  • 03

    Script polls POST /api/auth/token until user completes login

  • 04

    Receives access_token + refresh_token. Caches refresh token in ~/.oma_token

  • 05

    Subsequent runs refresh silently — no browser interaction needed

# test_api_auth.sh
# 1. try silent refresh
curl -s -X POST /api/auth/token \
  -d grant_type=refresh_token \
  -d refresh_token=$CACHED

# 2. use access token
curl -H "Authorization: Bearer $TOKEN" \
  https://oma.example.org/api/proteins/

07
Token Validation

Does every request hit Keycloak?

No — validation is local, inside oauth2-proxy

On startup, oauth2-proxy fetches Keycloak's public keys from the JWKS endpoint (…/realms/myrealm/protocol/openid-connect/certs) and caches them in memory. Every Bearer token is then verified locally — signature, expiry, and audience — with no network round-trip per request.

Per request

  • Signature verified against cached JWKS

  • Expiry (exp) checked locally

  • Audience (aud) checked locally

~0 ms overhead

Keycloak contacted when

  • oauth2-proxy starts (fetch JWKS)

  • Browser login redirect

  • Token issuance / refresh via /api/auth/token

  • Periodic JWKS key rotation refresh

Implication

  • A revoked token stays valid until it expires (up to 5 min)

  • Acceptable for most use cases; shorten access token lifespan if stricter revocation is needed

08
Security Properties

What We Get

  • Client secret never reaches the client. nginx injects credentials into /api/auth/* requests server-side before proxying to Keycloak.

  • Session cookies are encrypted with a random 32-byte key (OAUTH2_PROXY_COOKIE_SECRET). Tamper-proof.

  • Short-lived access tokens (5 min) minimize the window for token theft. Refresh tokens extend sessions without re-login.

  • nginx enforces auth at the edge via auth_request. Every protected /api/ call is checked before Django is reached. Bearer tokens are verified by oauth2-proxy against cached JWKS, no Keycloak round-trip per request.

  • Website AJAX bypass uses sec-fetch-site: same-origin, a browser-enforced Fetch Metadata header that scripts cannot forge, so the public site stays fully functional without leaking the API to external clients.

  • Edu-ID workaround (temporary): INSECURE_OIDC_ALLOW_UNVERIFIED_EMAIL=true is set while LifeScience login integration with Keycloak is being resolved. Will be reverted once fixed.

  • Identity forwarded to Django via X-Auth-Request-User and X-Auth-Request-Email, ready for future per-user logic without rework.

What changed in the repo

  • docker-compose.yml — nginx is now the public entry point (ports: 80:80); oauth2-proxy moved to expose: (internal auth service); OAUTH2_PROXY_UPSTREAMS=static://200 (forward-auth mode); OAUTH2_PROXY_SKIP_AUTH_ROUTES removed

  • nginx/nginx.conf.template — /_auth_check internal location checks sec-fetch-site: same-origin; /oauth2/ proxy and internal /oauth2/auth for auth_request; /oma/ and /api/ split into separate location blocks; 401 returns JSON or redirects to sign-in based on sec-fetch-mode

  • env.template — variables documented

  • test_api_auth.sh — reference script for programmatic auth

  • AUTHENTICATION.md — full architecture & setup guide

Zero changes to Django application code.

Network isolation

Bind the internal nginx vhost to 127.0.0.1 only — equivalent to Docker's expose:. Verify with ss -tlnp | grep 8080.

Secret management

Store variables in /etc/oauth2-proxy/env (chmod 600, owned by the service user). Same variables as the Docker .env file.

Process supervision

Run oauth2-proxy as a systemd unit with EnvironmentFile= and Restart=on-failure. No other changes to nginx or Django required.

Next Steps

Open Questions & Proposals

1. Selective endpoint protection

Now that nginx handles routing, expose a specific endpoint by adding a dedicated nginx location block above the protected /api/ block, without auth_request.

  • More specific location matches first, so the public endpoint takes precedence

  • Versioned in nginx.conf.template, changes tracked via git

  • Redeploy required to apply changes

2. Per-plan rate limiting

Tiers based on affiliation, not payment — managed as Keycloak roles, forwarded to nginx via X-Auth-Request-Groups.

TierWhoAssignment
guestNo tokenautomatic
registeredAny valid logindefault role
academicInstitutional email / Edu-IDidentity attribute
institutionalLabs contacting us directlymanual

If paid plans are ever needed: Stripe webhook promotes/demotes Keycloak role. Proxy layer stays unchanged.

3. Traffic analytics

Stay in Matomo. nginx logs API calls and forwards them as Matomo Events via the HTTP Tracking API.

  • X-Auth-Request-User used as custom dimension → split guest vs authenticated in dashboards

  • Endpoint path + HTTP method tracked as event category/action

  • Single analytics platform, no new tooling required

4. Custom oauth2-proxy UI

oauth2-proxy serves its own sign-in and error pages. These can be replaced with custom HTML templates mounted via Docker volume.

  • Brand the sign-in page with OMA logo and styles

  • Custom error pages (401, 403, 5xx) with helpful messaging

  • Configured via --custom-sign-in-logo and --custom-templates-path
